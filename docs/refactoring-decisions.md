# 2026 年 11 月の作り直しで決めたこと

2026-11-18〜19 に、変換器とランタイムの構成を作り直しました (タグ `refactor-base` から)。手順と実施記録は、開発用の手順書 `refactor-plan.md` にあります。この文書には、その中で決めたこととその理由を残します。

## 作り直しの段階

| 段階 | 内容 |
|---|---|
| Phase 0 | 回帰の確認の仕組み: 14 作品 × 2 言語の変換結果の比較 (`tools/golden.py`) と、決まった乱数の種でのリプレイ (`tools/replay.py`) |
| Phase 1 | 使っていないコードの削除、ランタイムの公開名の一覧、AST とコンパイル時の処理を `zilpy/front`・`zilpy/compiletime` に分ける |
| Phase 2 | コンパイル時の条件の評価 (`static_eval.py`) と AST の変形 (`lowering.py`) を分ける。Python 版と Lua 版の変換器に共通の骨組み (`zilpy/backend/base.py`)。名前の解決 (`names.py`) |
| Phase 3 | コンパイル時の MDL 評価器 (`mdl.py`)。作品の `DEFMAC` を作品の定義どおりに展開する。共通マクロの確認、マクロの関数化、マクロの注記 |
| Phase 4 | ランタイムに手で書いていたマクロ相当の関数 17 個を削除する (共通マクロだけを残す) |
| Phase 5 | ランタイムを入口のファイルと `zilrt/` パッケージに分ける |
| Phase 6 | 元の ZIL へたどる情報: 位置の注記、`zilmap.json`、ZIL のコメント、ZIL の名前での登録、実行時エラーの ZIL の位置、`--zil-source` |
| Phase 7 | README と文書の更新、全作品の通しプレイ |

どの段階でも、作品の動きを変える変更は、変わる内容をリプレイで確かめてから入れました。動きが変わったのは `PROB` の修正 (下の 1) だけです。

## 決めたこと

### 1. `PROB` は作品の定義どおりにする

`PROB` (確率の判定) の定義は、作品によって `>=` と `>` の違いがあります (`LOSER?` があれば `ZPROB` を使う作品もあります)。前のランタイムは 1 つの定義ですべての作品を動かしていたので、境界の値で原作と結果が違いました。作品の定義をそのまま展開するように直しました。この修正で、HHGG と Trinity のリプレイの結果が変わりました (乱数の境界の値に当たる場面があるため)。

### 2. `TELL` は `TELL(...)` の形のまま出力する

`TELL` の書式指定子 (`D`、`A` など) とルーチンの対応は、作品の `DEFMAC TELL` を評価器で展開して作ります。ただし、`TELL` そのものは展開せず、生成コードには `TELL(...)` の形で残します。展開すると、1 つの `TELL` が何行もの出力の呼び出しになり、元の ZIL と見比べにくくなるためです。

### 3. ランタイムはパッケージにする

ランタイムは、入口のファイル (`ZilRuntime.py` / `ZilRuntime.lua`) と、中身の `zilrt/` に分けました。変換するたびに、出力先へこの 2 つをコピーします。出力先のフォルダーだけで動くように、ランタイムを生成コードと同じ場所に置きます。Python 版では、前の 1 ファイルの形のときに保存したセーブファイルも読めます。

### 4. 手書きのマクロ関数は消し、共通マクロは残す

前のランタイムには、作品の `DEFMAC` の代わりに手で書いた関数がありました。評価器で作品の定義どおりに展開できるようになったので、共通マクロ以外の 17 個は消しました。

### 5. 辞書と構文テーブルは、今までどおり実行時に作る

辞書と構文テーブル (`SYNTAX`、`SYNONYM` など) を変換時に作ることも考えましたが、移しませんでした。生成コードに `SYNTAX(...)` の宣言が ZIL と同じ並びで残るほうが、元のソースと対応させやすいためです。ランタイムの中で `zilrt/vocab.py` (`vocab.lua`) に分けるだけにしました。

### 6. 名前が重なったら、ゲームの定義を使う

ゲームのルーチンとランタイムの関数が同じ名前のときは、ランタイムの内部からの呼び出しにもゲームの定義を使います。原作では、ゲームのルーチンがその名前の唯一の定義だからです。前は Lua 版だけがそうなっていたので、Python 版もそろえました。どちらを使うかは、変換するときに `--name-report` で一覧にできます。

### 7. Lua の演算子はランタイムの関数で呼ぶ

Lua 版では、算術やビット演算をランタイムの関数 (`ZG.ADD` など) で呼ぶ今の設計を続けます。Lua 5.1 にはビット演算の演算子がないためです。この方針は、変換器 (`zilpy/backend/lua.py`) の中でも守ります。

### 8. 共通マクロはランタイムに置き、違うときだけ上書きする

14 作品のどこでも同じ意味に定義されているマクロ 12 個 (`VERB?`、`PRSO?`、`RFATAL` など) は、ランタイムの組み込みの関数にしました。変換するときに作品の定義を試しに展開して、組み込みと同じ意味かを確かめます。違えば、作品の定義から同じ名前の関数を作って組み込みを上書きします (可変長の引数のマクロは、引数の数ごとに関数を作ります)。今の 14 作品で上書きした作品はありません。12 個の一覧は README の「共通マクロ」にあります。

ほかに、次のことも決めました。

- **効果音:** `IFSOUND` の中のコードは作品の定義どおりに入れ、効果音を鳴らすルーチン (Lurking Horror の `SOUNDS`) は、何もしない関数にします (`zilpy/constants.py` の `SILENT_ROUTINES`)。
- **元の ZIL の位置の注記とコメント:** 既定で出力します。`--no-zil-locations`・`--no-zil-comments`・`--no-macro-comments` で消せます。ZIL の原文の埋め込み (`--zil-source`) は既定ではオフです。原文がそのまま入るので、ライセンスのない作品では、生成物を配布しないときだけ使います。

## 残っていること

- リポジトリの直下にあった変換器のモジュール (`ZilLexer.py`・`ZilConstants.py` など) は `zilpy/` へ移し、互換のための入口 (`ZilNodes.py`・`ZilTranscoder.py`・`ZilToLuaTranscoder.py`) は消しました (2026-11-19)。前の名前で import している外のコードは、`zilpy.` から始まる名前に直す必要があります (対応は README の「ソースコードの構成」)。
- `TELL` の完全な展開 (上の 2 の、次の段階) はしていません。
- Lua 版の実行時エラーの ZIL の呼び出しの並びには、末尾呼び出しをしたルーチンが出ません。

## 確かめ方

作り直しの間、次の 3 つで、変更のたびに動きが変わっていないことを確かめました。

```powershell
python tools/golden.py check   # 14 作品 × 2 言語の変換結果を、保存してある結果と比べる
python tools/replay.py check   # 決まった乱数の種 (1, 2, 3) で、リプレイの出力を比べる。Python 版と Lua 版の出力も比べる
python -m unittest             # 単体テスト
```

`tools/golden.py update`・`tools/replay.py update` で、保存してある結果を今の出力に置き換えます。差分を全部読んでから置き換えてください。
